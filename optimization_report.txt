
Optimization Report: Accelerating the Sieve of Eratosthenes Using Sequential, OpenMP, and CUDA Techniques

1. Sequential Implementation

The baseline version of the Sieve of Eratosthenes algorithm employs a straightforward approach to identifying prime numbers up to a given integer limit `n`. This implementation uses a boolean array of size `n+1` to mark primality. Initially, all values are set to true (indicating potential primality), except for indices 0 and 1, which are marked as false.

Algorithmically, the method iterates from 2 to √n. For each number `i` that remains marked as prime, all its multiples starting from `i*i` are marked as non-prime (false). The reason for starting from `i*i` is that all smaller multiples would have been marked by smaller primes.

- Time Complexity: O(n log log n) — optimal for this class of problems.
- Space Complexity: O(n) — requires memory proportional to the size of the number range.
- Bottleneck: The single-threaded execution becomes prohibitively slow for values of n approaching 10^9 due to the sheer volume of operations required.

This sequential implementation serves as the reference for evaluating the performance gains achieved through parallelization.

2. Parallelization Opportunities in the Sieve Algorithm

The Sieve of Eratosthenes naturally supports parallelization due to its independent computation structure:

- Independent Loops: Each prime candidate's multiples can be processed independently of others.
- No Write Conflicts (if managed carefully): When marking multiples of different primes, threads do not typically access overlapping memory locations if iteration ranges are properly assigned.
- Regular Memory Access: The memory access pattern is predictable, which can help with prefetching and vectorization on some hardware.

Key areas suitable for parallel execution:
- The outer loop that iterates through potential primes (i from 2 to √n).
- The inner loop that marks multiples of the current prime.

However, concurrency control and memory consistency must be carefully managed to avoid data races, especially in shared memory models like OpenMP.

3. OpenMP Parallel Implementation

OpenMP allows for shared-memory parallelization with minimal code modification through compiler directives. For this implementation:

Step 1: Parallelizing the Outer Loop
The outer loop (for i from 2 to √n) is parallelized because each iteration operates on a unique range of numbers. The directive:

#pragma omp parallel for schedule(dynamic)

is used to distribute the work dynamically among threads. The dynamic schedule helps mitigate load imbalance that naturally occurs due to decreasing iteration count in the inner loop as i increases.

Step 2: Inner Loop Left Sequential
The inner loop, responsible for marking multiples, is intentionally kept sequential within each thread for several reasons:
- Potential for race conditions when multiple threads attempt to write to the same index.
- Overhead of nested parallelism often outweighs the benefits at this fine granularity.
- Improved cache locality by letting a single thread handle contiguous memory regions.

Step 3: Optimization — Skipping Even Numbers
After treating 2 as a special case, the algorithm skips all even numbers:
- This halves the number of iterations.
- Reduces memory usage by approximately 50%.
- Significant performance gains without altering algorithm correctness.

Updated loop:
for (int i = 3; i <= sqrt(n); i += 2)

OpenMP allows leveraging all available logical CPU cores. With 16 threads (omp_set_num_threads(16)), this version sees substantial acceleration over the sequential version, particularly for n ≥ 10^8.

4. CUDA GPU Implementation

CUDA allows for highly parallel processing by launching thousands of lightweight threads on GPU cores. The CUDA implementation of the Sieve algorithm uses the following approach:

Step 1: Memory Allocation
- A boolean array is initialized on the host and copied to the device using cudaMemcpy.
- The array size is (n + 1) to accommodate all possible values.

Step 2: Kernel Execution
A CUDA kernel is launched for each prime `i`. The kernel `mark_multiples` marks a subset of `i`'s multiples, with each thread responsible for marking one or more positions:

__global__ void mark_multiples(bool* primes, int n, int i) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int start = i * i + idx * 2 * i;
    if (start <= n && start >= 0) {
        primes[start] = false;
    }
}

- Threads per block and block count are computed dynamically based on the number of multiples.
- cudaDeviceSynchronize() ensures that kernel execution is completed before proceeding to the next prime.

Step 3: Performance Considerations
- Kernel Launch Overhead: For each i, a separate kernel launch is required, which introduces overhead.
- Memory Bandwidth: Performance is highly dependent on the memory throughput of the GPU.
- Device Limitations: For very large n (e.g., 10^9), GPU memory usage becomes a constraint.

Step 4: Optimization — Skipping Even Numbers
As with the OpenMP version, even numbers are skipped to halve the workload. Each thread marks multiples spaced 2i apart starting from i².

5. Benchmarking and Evaluation

Benchmarking was performed using three versions:
- Sequential (CPU)
- Parallel (OpenMP with 16 threads)
- GPU (CUDA)

Tested values:
n = 10^7, 10^8, 10^9

Metrics:
- Execution time (in seconds) measured using high-resolution clocks.
- Output written to separate files for CPU (benchmark.txt) and GPU (benchmark_cuda.txt).
- All tests run on a 16-core CPU with NVIDIA GPU support.

Expected Performance Patterns:
- Sequential: Linear slowdown with increasing n.
- OpenMP: Near-linear speedup with increasing thread count, limited by memory bandwidth and false sharing.
- CUDA: Best performance for large n, but diminishing returns due to kernel launch cost and synchronization overhead for smaller n.

6. Conclusion

This report demonstrates the efficiency gains from optimizing and parallelizing the Sieve of Eratosthenes across three computation paradigms:

- The sequential version serves as a baseline.
- The OpenMP version leverages multi-core CPUs and benefits from careful workload balancing and domain-specific optimizations.
- The CUDA version achieves maximum parallel throughput, suitable for large-scale data sizes but requires careful resource management.

Key insights:
- Skipping even numbers provides a consistent and substantial optimization.
- Memory access patterns and write contention are critical to scalability.
- Each architecture (CPU vs. GPU) favors different optimization strategies.

Future work could explore:
- Bit-packed storage to further reduce memory usage.
- Hybrid approaches (CPU-GPU cooperation).
- SIMD vectorization on CPUs using intrinsics.

These implementations and their evaluations illustrate the importance of choosing the right parallel model based on problem size and hardware characteristics.
