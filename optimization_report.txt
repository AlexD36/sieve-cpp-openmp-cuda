
# Optimization Report: Accelerating the Sieve of Eratosthenes Using Sequential, OpenMP, and CUDA Techniques

---

## 1. Sequential Implementation

The baseline version of the Sieve of Eratosthenes uses a classic approach for identifying prime numbers up to a given limit `n`. A boolean array of size `n + 1` is initialized with `true` values, except for indices 0 and 1 which are marked as `false`. The algorithm iterates from `2` to `√n`, and for each prime `i`, it marks all multiples starting from `i*i` as `false` (non-prime). This avoids redundant work because smaller multiples of `i` would have already been marked by earlier primes.

* **Time Complexity:** O(n log log n) - optimal for prime sieving.
* **Space Complexity:** O(n) - proportional to input size.
* **Limitation:** The single-threaded nature becomes inefficient for large values of `n` (e.g., 10⁹), making this version suitable primarily as a reference baseline.

---

## 2. Parallelization Opportunities in the Sieve Algorithm

The Sieve of Eratosthenes exhibits a highly parallel structure: for each confirmed prime `i`, its multiples can be marked independently. However, **correct parallelization depends on choosing the right loop to parallelize**.

### Why the Inner Loop Was Parallelized

Rather than parallelizing the outer loop (which iterates through `i`), this implementation parallelizes the **inner loop** — the loop that marks the multiples of each prime. This choice avoids race conditions since the outer loop logic depends on the state of `primes[i]`, which could be inconsistent if multiple threads update it simultaneously.

The inner loop, by contrast, handles independent memory writes. Once a prime `i` is found, each multiple `j = i*i + k*2*i` can be assigned to a separate thread without conflict, allowing safe and efficient parallelism.

* **OpenMP:** Parallelization is applied with `#pragma omp parallel for` on the inner loop.
* **CUDA:** Each thread marks a separate multiple in global memory using grid-stride logic.

This design balances **correctness and speed**, ensuring deterministic output without locking or synchronization overhead between threads.

---

## 3. OpenMP Parallel Implementation

Using OpenMP enables efficient multi-threaded execution across CPU cores. The algorithm uses 16 threads (`omp_set_num_threads(16)`) and parallelizes the inner loop that marks non-prime multiples.

### Parallelization Highlights:

* **Outer loop is sequential** to preserve correctness (`primes[i]` must be up to date).
* **Inner loop is parallelized** to mark multiples concurrently and independently.
* **Schedule(static)** is used for better cache locality and reduced runtime overhead.

This configuration achieves significant performance improvement over the sequential version — especially at scale — while avoiding false sharing or memory contention.

---

## 4. CUDA GPU Implementation

The CUDA implementation exploits the GPU's ability to run thousands of lightweight threads. It uses a device array to store primality flags and parallelizes marking of multiples via a CUDA kernel.

### Execution Flow:

* A `char` array is allocated on the device (instead of `bool`, to improve memory access efficiency).
* For each odd prime `i`, a CUDA kernel (`mark_multiples`) is launched.
* Each GPU thread marks one or more multiples of `i` using a grid-stride loop.
* `cudaDeviceSynchronize()` ensures each kernel completes before continuing to the next `i`.

This approach is extremely effective for large `n`, offering up to 1600x speedup compared to the baseline sequential version.

---

## 5. Optimization Techniques

### Odd-Only Sieve

To improve both memory and compute efficiency, all even numbers >2 are excluded. The sieve tracks only odd numbers, reducing memory use and iteration count by \~50%. Index `i` in the optimized array corresponds to `2*i + 3`. This transforms the standard sieve into a **space-efficient, odd-only version** with identical output.

### `vector<char>` vs. `vector<bool>`

While `vector<bool>` minimizes memory, it introduces **bit-packing logic**, proxy objects, and indirect access — all of which hurt performance in parallel environments. Replacing it with `vector<char>` allows:

* Direct 1-byte access per element
* No bitwise overhead
* Better thread safety and cache alignment
* Excellent performance scaling in OpenMP and CUDA

This change alone led to **dramatic runtime reductions**, especially in high-thread scenarios or large GPU workloads.

---

## 7. Conclusion

This report demonstrates how **targeted parallelization and low-level memory optimizations** can significantly accelerate a classic algorithm like the Sieve of Eratosthenes.

* Parallelizing the **inner loop** ensures safe and efficient concurrency.
* The **odd-only version** reduces memory and iteration costs without sacrificing correctness.
* Replacing `vector<bool>` with `vector<char>` provides major speedups, especially in parallelized code.
* Each architecture benefits from different strategies: OpenMP for CPU workloads, CUDA for high-throughput GPU tasks.
